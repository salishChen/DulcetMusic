# 愉乐音乐播放器：优化建议

> 基于 `android` 分支当前工作树（基线提交 `520e469`，2026-09-25）的静态代码审查。优先级：**P0** 为正式发布前应处理的安全/发布问题，**P1** 为可复现或代码路径可明确推导的功能正确性问题，**P2** 为性能、体验与维护性改进。建议不代表已经修改实现。

## 建议概览

| 编号 | 优先级 | 建议 | 主要收益 |
| --- | --- | --- | --- |
| 01 | P0 | 保护 Subsonic 凭据，移除持久化及日志中的认证 URL | 降低账号凭据暴露风险 |
| 02 | P0 | 改用正式发布签名并建立发布校验 | 避免用调试密钥分发正式包 |
| 03 | P1 | 修复重新扫描的歌曲合并语义 | 保留喜欢、统计、歌词和歌单关联 |
| 04 | P1 | 以内容 URI 处理媒体库和所选目录 | 提升分区存储、SD 卡与文档提供方兼容性 |
| 05 | P1 | 统一缓存文件、数据库记录与容量统计 | 防止清空后封面失效、淘汰失准 |
| 06 | P1 | 保证并发缓存任务取消后所有等待者结束 | 防止同曲下载请求悬挂 |
| 07 | P1 | 用全库聚合生成播放概览 | 修正播放记录多于 50 首时的统计值 |
| 08 | P1 | 让“测试连接”不写入配置 | 测试失败时保留已有服务器配置 |
| 09 | P1 | 保留队列原始顺序并按下标定位重复曲 | 修正重启后随机队列及重复曲播放 |
| 10 | P2 | 优化扫描索引与专辑标识 | 降低大曲库扫描成本，避免同名专辑混合 |
| 11 | P2 | 补齐数据、缓存、播放的回归测试 | 让上述修复可持续验证 |
| 12 | P2 | 统一版本信息并检查主线程图片解码 | 减少界面误导和切歌卡顿 |

## 01. 保护 Subsonic 凭据和认证 URL（P0）

**现状与影响**：`subsonic_config.password` 以文本列保存在 SQLite；构造的流地址包含用户名、随机盐和认证 token，并作为歌曲 `path` / `remoteStreamUrl` 写入数据库。HTTP 请求失败时，网络层异常或缓存层日志会输出完整 URL。应用允许自动备份，也全局允许明文 HTTP。这样会扩大凭据及认证参数的存储、备份、日志与网络暴露面。这里的 URL **不含明文密码**，但包含可用于认证的参数。

**建议**：

1. 将服务器密码迁移到受 Android Keystore 保护的加密存储；数据库只保存非敏感配置及凭据引用，并对旧库做一次安全迁移。
2. 数据库仅保存服务器标识、远程歌曲 ID 等稳定信息；在播放/下载时临时生成带认证参数的流地址，不把完整认证 URL 持久化。
3. 日志和错误消息只显示端点、HTTP 状态及去敏感化主机信息，统一删除 `u/s/t` 等查询参数；检查异常向界面传递时是否携带完整 URL。
4. 为账号数据配置备份排除规则；默认推荐 HTTPS。若要兼容用户自建 HTTP 服务器，应让用户显式选择并仅在该连接场景使用。

**验收**：升级已有配置后仍可连接；新写入的数据库与备份不含明文密码或含认证参数的 URL；断网、HTTP 失败和下载失败日志均不出现 `u=`、`s=`、`t=`；HTTPS 与用户明确配置的 HTTP 场景分别验证。

代码依据：[数据库结构](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/MusicDatabase.kt)、[配置 DAO](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/SubsonicConfigDao.kt)、[Subsonic 客户端](../core/network/src/main/kotlin/com/mtechviral/musicfinderexample/core/network/SubsonicService.kt)、[缓存下载](../core/cache/src/main/kotlin/com/mtechviral/musicfinderexample/core/cache/CacheService.kt)、[应用清单](../app/src/main/AndroidManifest.xml)。平台参考：[Android 备份安全建议](https://developer.android.com/privacy-and-security/risks/backup-best-practices)、[Android 网络安全配置](https://developer.android.com/privacy-and-security/security-config)。

## 02. 建立正式发布签名与版本校验（P0）

**现状与影响**：`release` 构建明确设置 `signingConfig = signingConfigs.getByName("debug")`。若直接发布该产物，会使用调试密钥。代码还关闭了 release 压缩/混淆；后者属于按包体与调试需求评估的改进，不是阻断项。

**建议**：把正式签名凭据交由本机安全配置或 CI 密钥管理提供，构建脚本不引用 debug 签名；在发布流水线执行 APK/AAB 签名证书校验、版本号递增校验。按需要启用 R8 并验证 Media3、序列化及反射相关保留规则。

**验收**：release 包的证书指纹与正式签名一致且与 debug 不同；密钥不进入仓库；升级安装和核心播放/远程功能通过发布包验证。

代码依据：[app/build.gradle.kts](../app/build.gradle.kts)、[proguard-rules.pro](../app/proguard-rules.pro)。

## 03. 修复重新扫描覆盖用户状态和歌单关系（P1）

**已确认的代码路径**：入库先按“歌名｜艺术家｜专辑”建立索引。同身份同来源直接跳过，导致重扫不会更新变动的标签和远程地址；同身份不同来源时将新扫描对象的全部字段覆盖到旧行，新对象默认的 `isLiked=false`、`playCount=0`、`lastPlayed=null`、`lyrics=null`、缓存路径为空等会清掉用户状态。若音频路径不变但身份字段变化，新身份分支使用 `INSERT OR REPLACE`；旧行可能被删除，外键级联解除歌单关联。

**建议**：将“扫描得到的元数据”和“用户产生的状态”分字段更新；以稳定的来源标识与本地 URI/远程服务器 ID + 歌曲 ID 做匹配，明确跨来源冲突策略。已有歌曲更新时保留主键及歌单绑定，避免对歌曲表使用 `REPLACE`。同来源重扫允许更新元数据，但保留喜欢、播放统计、缓存及有价值的已有歌词。

**验收**：给歌曲加喜欢、播放次数和歌单绑定后，分别执行同源重扫、跨源同名导入、同路径改标签重扫，用户状态与歌单绑定仍符合预期；换 Subsonic 服务器后不会误复用旧服务器的远程 ID/流地址。

代码依据：[SongDao.insertSongs](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/SongDao.kt)、[SongMapper.toContentValues](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/SongMapper.kt)、[外键与表结构](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/MusicDatabase.kt)。

## 04. 以内容 URI 完成媒体库和文件夹扫描（P1）

**现状与影响**：媒体库扫描只取 `MediaStore.Audio.Media.DATA` 绝对路径；目录选择返回树 URI 后，页面尝试推导真实路径，扫描服务再用 `File.walkTopDown()` 遍历。文档提供方或不同存储卷不保证有可用的真实路径，树 URI 的访问授权也不能替代对任意路径的 `File` 访问。当前无法解析时要求用户手动输入路径，可能出现已选目录但扫描为空的体验。

**建议**：媒体库保留媒体项 URI，以 `ContentResolver` 打开文件描述符供元数据解析与播放；所选目录按树 URI 遍历 `DocumentFile`/`DocumentsContract`，为需要重启后访问的目录保存 URI 授权。把数据库中的“资源定位”抽象为本地路径或内容 URI，删除操作也按资源类型处理。完成后评估是否仍需要 `MANAGE_EXTERNAL_STORAGE` 声明。

**验收**：在受支持的 Android 版本、外置 SD 卡及非本机路径的文档提供方上，选目录后能扫描、播放并在重启后继续访问；拒绝权限与提供方失效时显示明确错误而非零首成功。

代码依据：[扫描页](../feature/scan/src/main/kotlin/com/mtechviral/musicfinderexample/feature/scan/ScanScreen.kt)、[扫描服务](../core/media/src/main/kotlin/com/mtechviral/musicfinderexample/core/media/MetadataScanService.kt)、[元数据解析](../core/media/src/main/kotlin/com/mtechviral/musicfinderexample/core/media/MetadataParser.kt)、[权限清单](../app/src/main/AndroidManifest.xml)。平台参考：[Android 文档与目录访问](https://developer.android.com/training/data-storage/shared/documents-files)。

## 05. 统一缓存状态与容量规则（P1）

**已确认的问题**：`clearAllCache()` 删除整个缓存目录后只清理音频 `cachedPath`，未清理数据库中的 `cachedArtworkPath`。启动补封面仅查询封面路径为空的曲目，所以“清空全部缓存 → 重启”后有些远程封面不会重新下载。容量统计包含整个缓存目录，淘汰却只遍历已登记的音频文件；删除音频失败时仍扣减待释放字节并清除数据库记录。播放命中缓存文件时不刷新缓存时间戳，现有策略也不是严格的 LRU。

**建议**：让清空操作同时重置音频/封面数据库字段，按同一份目录清单核对 `.tmp`、音频、封面和孤儿文件；文件删除失败时保留记录并返回失败；每次下载、命中或播放按统一规则更新“最近使用”时间。缓存容量阈值应覆盖音频与封面，必要时给封面设独立预算。

**验收**：远程歌曲有封面时执行清空并重启，目录和数据库缓存字段均为空，封面可重新获取；模拟删除失败时不虚报已释放空间；设置低容量后所有缓存文件总和仍受上限约束；缓存 A、B，重播 A，再缓存 C 触发淘汰时优先淘汰 B。

代码依据：[CacheService.clearAllCache/evictIfNeeded](../core/cache/src/main/kotlin/com/mtechviral/musicfinderexample/core/cache/CacheService.kt)、[SongDao 缓存查询](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/SongDao.kt)、[启动补封面](../app/src/main/kotlin/com/mtechviral/musicfinderexample/YuleMusicApplication.kt)、[播放缓存命中](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlayerController.kt)。

## 06. 让并发缓存任务在取消和异常后可靠结束（P1）

**条件性缺陷**：同一远程 ID 的并发下载使用 `CompletableDeferred` 合并任务。任务所有者在 `doCacheSong()` 意外取消或抛出未捕获异常时，代码从 `finally` 移除登记，却可能未执行 `task.complete(result)`；已经拿到该任务的等待者会一直挂起。封面内存缓存也使用类似的在途任务模式。

**建议**：把成功、失败和取消都作为明确的完成结果传播给所有等待者；在释放在途任务登记前先保证其已完成。用 `try/catch/finally` 覆盖 `CancellationException`，保留协程取消语义，同时向其他等待者返回可重试结果或同一失败原因。

**验收**：同一首歌/封面同时发起两次请求，取消第一个调用后第二个能在有限时间内成功、失败或收到取消，随后可重试；不会残留 `.tmp` 或在途登记。

代码依据：[CacheService.cacheSong](../core/cache/src/main/kotlin/com/mtechviral/musicfinderexample/core/cache/CacheService.kt)、[ArtworkCache](../core/media/src/main/kotlin/com/mtechviral/musicfinderexample/core/media/ArtworkCache.kt)。

## 07. 从全库聚合统计概览（P1）

**已确认的问题**：统计页只查询“最常播放”前 50 首，然后用这 50 首的播放次数求和、用列表长度计算“已听歌曲”。超过 50 首歌曲有播放记录时，“总播放次数”和“已听歌曲”会低于真实值；“最近播放”卡片数字也受最近 50 条列表上限影响。

**建议**：为概览提供独立的 SQL 聚合查询，例如对全部 `playCount` 求和、对 `playCount > 0` 的歌曲计数；明确“最近播放”卡片的时间窗口或改为“最近列表条数”，列表查询仍可保持 50 首分页/限额。

**验收**：准备 60 首各播放一次的歌曲，概览至少显示 60 次与 60 首，排行仍可只显示 50 首；播放一次后概览即时刷新。

代码依据：[StatsScreen](../feature/stats/src/main/kotlin/com/mtechviral/musicfinderexample/feature/stats/StatsScreen.kt)、[统计查询](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/SongDao.kt)。

## 08. 分离“测试连接”和“保存配置”（P1）

**已确认的问题**：远程配置页点击“测试连接”时，先把临时表单调用 `saveConfig()` 写入数据库，然后才执行 `ping()`。即使测试失败，新配置也已持久化，下一次进入或重启后可能使用失败的服务器。

**建议**：提供接收临时配置的连接测试方法，不修改数据库及当前活跃配置；只有“保存配置”明确提交成功后才更新持久化记录。测试中区分网络不可达、认证失败和地址格式错误。

**验收**：原配置 A 可用、表单改为不可达 B，点击“测试连接”后提示失败，重启应用仍使用 A；明确点击“保存配置”后才切换到 B。

代码依据：[SubsonicConfigScreen](../feature/subsonic/src/main/kotlin/com/mtechviral/musicfinderexample/feature/subsonic/SubsonicConfigScreen.kt)、[SubsonicService.saveConfig/ping](../core/network/src/main/kotlin/com/mtechviral/musicfinderexample/core/network/SubsonicService.kt)。

## 09. 修正随机队列恢复与重复曲定位（P1）

**已确认的代码路径**：随机模式下保存的是已经打乱的当前队列；恢复时又以该队列作为原始顺序执行随机化，切回顺序模式无法找回入列顺序。`playSongs(startIndex)` 通过目标歌曲 `path` 再定位，同一个路径在队列出现两次时，指定第二项可能落到第一项。

**建议**：持久化队列的稳定条目 ID、原始顺序、当前顺序和当前索引；从指定位置播放时直接使用索引/条目 ID，不再按路径反查首个匹配项。旧版偏好恢复时保留兼容回退。

**验收**：队列 `[A,B,C]` 切随机、重启、再切顺序后仍为 `[A,B,C]`；队列 `[A,A]` 从索引 1 开始，当前索引保持 1；插入/删除后重启仍定位同一条目。

代码依据：[PlaylistRepository](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlaylistRepository.kt)、[PlayerController.playSongs](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlayerController.kt)。

## 10. 优化大曲库扫描和专辑身份（P2）

**现状**：每批 `insertSongs()` 都从全表读取已有歌曲并建立身份索引；本地按 30 首、远程按 50 首分批，曲库越大重复读取越多。专辑聚合及详情只按专辑名分组/过滤，不同艺术家的同名专辑会显示为同一专辑。

**建议**：扫描周期只构建一次现有歌曲索引，或增加稳定身份/来源索引并使用事务化 UPSERT；远程 ID 也建立适当索引。专辑改用稳定专辑 ID，或至少使用“专辑名 + 专辑艺术家”复合键，并同步修改详情路由及旧数据迁移。

**验收**：在固定 1 万首测试库上记录扫描耗时和数据库查询次数，优化后重复全表读取显著减少；两个不同艺术家的同名专辑在列表和详情中各自展示正确曲目。

代码依据：[SongDao.insertSongs](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/SongDao.kt)、[MetadataScanService](../core/media/src/main/kotlin/com/mtechviral/musicfinderexample/core/media/MetadataScanService.kt)、[远程批量导入](../feature/scan/src/main/kotlin/com/mtechviral/musicfinderexample/feature/scan/ScanScreen.kt)、[AlbumDao](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/dao/AlbumDao.kt)。

## 11. 建立围绕真实数据的回归测试（P2）

**现状**：仓库目前仅有 `core:common` 的 LRC 解析与排除列表两组单元测试，数据库迁移、扫描覆盖、缓存、队列和 Subsonic 网络流程没有对应的自动化回归保障。

**建议顺序**：

1. SQLite 版本 1～6 升级样本；同路径改标签、同身份跨来源、歌单外键和喜欢/统计保留。
2. 缓存清空、下载中断、删除失败、并发取消；用临时目录与可控 HTTP 响应测试。
3. 随机队列重启恢复、重复曲索引；统计超过 50 首的聚合。
4. Subsonic 内网失败/公网回退、远程歌单重复同步、测试连接失败保留旧配置；用真实 `.mp3/.flac/.ogg/.opus` 样本验证内嵌歌词解析。

**验收**：上述每个已确认缺陷先有失败用例，再在修复后通过；CI 执行单元测试，涉及 Android 存储权限的场景加入仪器测试。

代码依据：[现有测试目录](../core/common/src/test/kotlin/com/mtechviral/musicfinderexample/core/common/)、[数据库](../core/database/src/main/kotlin/com/mtechviral/musicfinderexample/core/database/)、[内嵌歌词解析](../core/media/src/main/kotlin/com/mtechviral/musicfinderexample/core/media/EmbeddedLyricsReader.kt)。

## 12. 收敛版本信息与图片刷新成本（P2）

**现状**：构建配置的 `versionName` 为 `2.0.0`，设置页“关于”写死 `1.0.0`，用户看到的版本与安装包不一致。桌面小组件刷新时会读取/解码封面文件；在多组件或大封面情形下，需确认该工作是否占用主线程并重复执行。

**建议**：关于页从构建版本信息读取显示值；小组件封面在后台按目标尺寸解码、复用缩略图并限制高频重复刷新。

**验收**：关于页显示与安装包版本一致；切歌和播放状态更新时主线程无明显封面解码阻塞，小组件仍及时更新。

代码依据：[app/build.gradle.kts](../app/build.gradle.kts)、[SettingsScreen](../feature/settings/src/main/kotlin/com/mtechviral/musicfinderexample/feature/settings/SettingsScreen.kt)、[MusicWidgetProvider](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/MusicWidgetProvider.kt)、[MusicWidgetUpdater](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/MusicWidgetUpdater.kt)。

## 推荐实施顺序

1. 先处理 **01～02**，使账号数据和发布包满足基本安全要求。
2. 再处理 **03～09**，优先修复用户数据丢失、缓存失效和可见统计错误。
3. 每完成一项同步补充 **11** 中的回归用例，再处理 **10、12** 的性能与体验问题。
