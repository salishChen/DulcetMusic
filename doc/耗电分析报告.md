# 愉乐音乐播放器耗电分析报告

分析日期：2026-09-27  
代码基线：`df1628c`（当前工作区原生 Android 实现，Kotlin + Compose + Media3 1.9.4）  
分析方式：静态代码审查、调用链核对、Android 官方资料交叉验证。

## 1. 结论与适用范围

当前代码存在多条可以解释额外耗电的明确路径，优先处理：**远程播放与独立整曲缓存重复传输、悬浮歌词高频持久化及重复解析、EasyTier 保活范围过宽**。播放器全局进度轮询和启动时批量补封面会进一步增加后台工作量。

这些结论确认的是“额外工作确实会被代码触发”，尚不能确认它们各自占实际耗电的比例。本次没有取得手机型号、系统版本、异常发生场景、安装包版本、Batterystats 或系统跟踪数据；PATH、Android SDK 环境变量及常见 SDK 位置未发现可用 adb，未执行真机测量。不能据此给出每小时耗电百分比、毫安时数值或预计节电百分比，也不能断言某一项是用户设备上的唯一根因。

| 顺序 | 发现 | 主要触发场景 | 证据强度 | 建议优先级 |
|---|---|---|---|---|
| 1 | 当前歌曲流式播放与整曲缓存使用独立请求，另有下一首预缓存 | 手动播放未缓存远程歌曲，连续点歌 | 调用链已确认，实际重复字节数待测 | P1 |
| 2 | 悬浮歌词持续写偏好、发广播、重复解析和刷新 | 悬浮歌词开启，尤其后台播放 | 调用链和周期已确认 | P1 |
| 3 | EasyTier 按“远程歌曲”而非实际隧道使用保活 | 曾启动组网，随后播放缓存曲或直连远程歌曲 | 条件判断已确认，引擎功耗待测 | P1 |
| 4 | 播放进度轮询与界面订阅、屏幕状态脱钩 | 后台播放、暂停、服务断开后进程仍存活 | 生命周期与周期已确认 | P2 |
| 5 | 应用启动自动批量补封面，无电量/网络约束 | 远程曲库大、封面缺失、服务器不稳定 | 入口和批处理已确认 | P2 |
| 6 | 未见音频 offload 显式配置与运行状态监测 | 长时间本地/缓存音频熄屏播放 | 优化机会，是否实际未卸载待测 | P3 |

P1 表示优先修复的高价值问题，并非已证明占耗电最多；P2 表示后台开销治理；P3 需要设备能力和实测结果决定。

## 2. 远程播放与缓存重复传输

### 2.1 证据与调用链

- [PlayerController.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlayerController.kt)：257–299 行，`playAt()` 在 `prepare()/play()` 后，对未缓存远程歌曲调用 `CacheService.startCaching()`。
- [RemotePlaybackDataSource.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/RemotePlaybackDataSource.kt)：14–28 行，播放使用 `DefaultDataSource + StrictHttpDataSource` 直接读取远程流，没有共享下载缓存层。
- [CacheService.kt](../core/cache/src/main/kotlin/com/mtechviral/musicfinderexample/core/cache/CacheService.kt)：262–306、477–505 行，缓存另行取得流地址，用自己的 OkHttp 请求将整首歌曲写入文件。
- `PlayerController.kt`：830–853 行，每次播放收尾还调用 `precacheNext()` 下载下一首未缓存远程歌曲。

因此一次手动点播可能同时存在：当前曲播放流、当前曲整曲缓存、下一首整曲缓存。缓存服务的 `inFlight` 仅合并同一歌曲的缓存任务，无法合并播放器自己的流请求。

### 2.2 为什么可能耗电明显

额外下载增加无线网络传输与磁盘写入；快速切换不同歌曲时，每首歌各有独立缓存任务，旧歌曲缓存不会因选中另一首而自动停止。`startCaching()` 使用应用级作用域，`downloadToFile()` 同步 `execute()/copyTo()`，没有按下载块检查协程取消。全局源码中，`cancelPending()` 的调用位于远程源配置操作，暂停/普通切歌没有对应取消入口。

下载使用同步 `execute()`，不能仅依据 OkHttp 的异步请求并发配置推断任务已经限流；缓存层未见面向不同歌曲的显式并发上限。用户连续点播多个大文件时，后台任务可能堆积。

整曲缓存有利于后续离线播放，但当前实现为首次播放付出独立传输成本。不能直接称“耗电翻倍”或“流量必然三倍”：播放缓冲量、提前切歌、缓存命中、服务器转码都会改变实际字节数。

另一个可避免场景：`precacheNext()` 按 `(idx + 1) % size` 选下一首，没有检查单曲循环模式；单曲循环时仍可能下载不会立即播放的相邻歌曲。

### 2.3 建议与验收

1. 让播放器读取的数据直接进入共享缓存，例如评估 Media3 `CacheDataSource`，使用稳定且隔离数据源的缓存键；处理 Range、鉴权、淘汰和旧缓存兼容。
2. 将“用户明确下载”和“推测性预缓存”分开管理；预缓存先限制为一个任务，切歌时取消不再需要的任务，取消信号联动 `Call.cancel()`。
3. 预缓存按播放模式、网络是否计费、电量和缓存命中决策；单曲循环不预取相邻曲目。
4. 验收：服务端访问日志与客户端字节计数确认，普通首次播放不再为同一内容并发发起两套完整下载；连续点歌后旧预取及时结束。合法 Range/重试请求不能一概判为重复下载。

## 3. 悬浮歌词同步链路存在持续额外工作

### 3.1 证据与调用链

```text
PlayerController：播放中每 200 ms 读取进度
  → 进度与上次推送相差至少 500 ms 时 updateFloatingLyrics()
  → LyricsOverlayManager.updateLyrics()
  → SharedPreferences.apply() + ACTION_UPDATE_STATE 广播
  → FloatingLyricsService 接收广播
  → 读取设置 + 重新解析歌词 + 应用样式 + 更新文本

同时：FloatingLyricsService 自己每 200 ms 读取偏好并刷新歌词
```

关键位置：

- [PlayerController.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlayerController.kt)：62–69、1009–1050 行。
- [LyricsOverlayManager.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/LyricsOverlayManager.kt)：211–219、315–316 行，每次更新写歌词全文、位置、时间戳、播放状态并发广播。
- [FloatingLyricsService.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/FloatingLyricsService.kt)：158–197 行，广播与自身定时器并存；349–387、579–580 行，重新解析与重复赋值文本。

### 3.2 已确认的四个问题

**实时状态被当作持久化数据。** 播放进度和更新时间持续变化，每次 `apply()` 都引入持久化工作。Android 官方说明 `apply()` 先更新内存，再异步提交磁盘；异步不代表没有 I/O。实际文件写入次数可能受系统合并影响，不能把调用次数等同于闪存写入次数。[SharedPreferences.Editor 官方说明](https://developer.android.com/reference/android/content/SharedPreferences.Editor)

**广播路径绕过歌词去重。** 定时器的 `syncFromPrefs()` 有 `raw != lastRawLyrics` 判断，但广播的 `loadLyricsFromPrefs()` 直接调用 `parseAndSetLyrics()`。只要广播送达，即使歌词没有变化，也再次执行正则解析、集合创建和排序。此前“避免每 200 ms 重复解析”的注释只覆盖轮询通道。

**进度变化触发设置重应用。** 每次状态广播都会调用 `applyLyricsStyle()/applyLinesCount()`；播放中的定时器也重复设置 `TextView.text`，未按活动歌词行或文本内容去重。这里确认的是重复调用，具体布局和绘制成本需要跟踪测量。

**暂停或熄屏没有停表条件。** 定时器无论是否播放都在末尾继续 `postDelayed(200)`；暂停只是跳过文本刷新，仍读取偏好。全局检索未见屏幕交互状态判断。关闭服务时会移除回调，因此问题集中于服务仍存活时，不能称“关闭悬浮歌词后依旧每 200 ms 运行”。

### 3.3 理论频率

以下为设备可调度、正常 1 倍速连续播放时的代码频率估算，不是真机 CPU 唤醒计数：

| 工作 | 估算频率 | 一小时调用量 |
|---|---:|---:|
| 播放器进度轮询 | 5 次/秒 | 约 18,000 |
| 悬浮歌词自身轮询 | 5 次/秒 | 约 18,000 |
| 偏好提交与广播 | 通常每约 600 ms 一次 | 约 6,000 组 |
| 广播引发歌词重新解析 | 广播正常送达时与推送接近 | 约 6,000 |

500 ms 是位置差阈值，配合 200 ms 轮询通常在第三个周期触发，不能直接写成固定每秒两次。系统休眠、调度延迟、seek 和倍速会改变这些数字。

`Handler.postDelayed()` 与协程 `delay()` 本身不是唤醒闹钟，不能仅凭这些定时器证明设备一直不能深度休眠；后台播放已有 CPU 活动时，它们会继续叠加工作。偏好读取通常命中进程内缓存，也不能把每次读取都记成磁盘读取。

### 3.4 建议与验收

同进程使用 `StateFlow` 传递播放状态；SharedPreferences 仅保存颜色、字号、位置等用户设置。歌词只在歌曲或原文改变时解析，显示只在活动行改变时更新。使用单调时钟记录播放基准，seek/暂停/继续时更新，必要时低频校正；屏幕不可交互或没有可见歌词时停止显示定时任务。

验收：播放进度更新不再产生偏好持久化或状态广播；同一歌词解析次数接近加载/变更次数；暂停或熄屏后悬浮歌词显示定时任务停止，恢复亮屏后歌词能正确校准。

## 4. EasyTier 的按需运行条件不够精确

### 4.1 已有优化

[EasyTierEngine.kt](../core/easytier/src/main/kotlin/com/mtechviral/musicfinderexample/core/easytier/EasyTierEngine.kt) 已实现按需启动、15 分钟空闲停止；[EasyTierConfig.kt](../core/easytier/src/main/kotlin/com/mtechviral/musicfinderexample/core/easytier/EasyTierConfig.kt) 默认关闭引擎、默认启用省电运行参数。因此不能把 EasyTier 描述成所有用户启动软件后都会运行的常驻进程。

### 4.2 剩余问题

**保活条件只看歌曲来源。** `PlayerController.kt` 1020–1022 行，只要 `_currentSong.isRemote` 就调用 `touch()`，没有检查实际播放 URI、是否已缓存、是否经过 EasyTier。1148–1153 行又明确允许已缓存远程歌曲走本地文件。因此：引擎此前已启动时，播放缓存远程歌曲仍可不断刷新活动时间，令 15 分钟休眠失效。`touch()` 本身不启动引擎，必须保留这个触发前提。

**直连请求也可能启动组网。** [SubsonicService.kt](../core/network/src/main/kotlin/com/mtechviral/musicfinderexample/core/network/SubsonicService.kt) 138–148 行，在尚未选择实际连接地址前调用 `awaitRunning()`；已有 `activeBaseUrl` 时，无论它是隧道还是直连地址都 `touch()`。引擎启动检查启用开关，但这里未检查当前数据源是否绑定组网。

[YuleMusicApplication.kt](../app/src/main/kotlin/com/mtechviral/musicfinderexample/YuleMusicApplication.kt) 72–81 行仅在“向网络层注入转发地址”时过滤绑定关系，并不能阻止前述引擎启动。某个 Subsonic 源直连成功、组网实际未参与传输时，仍可能留下活动子进程。

**活动结束后保留较长尾部。** 引擎按最后一次 `touch()` 判断空闲，不是真实字节流量；停止远程播放后仍可能运行约 15 分钟，随后由每 30 秒检查的看门狗处理。休眠调度会使实际停止时间更晚。看门狗在线程启动后一直存在，即使引擎关闭也每 30 秒检查，属较低优先级开销。

### 4.3 建议与验收

按实际传输通道记录活动：绑定源、选中隧道、活跃流请求三个条件明确后才维持组网。用连接租约/引用计数覆盖长时间播放、下载和扫描，避免仅依赖请求开始时打点造成中途休眠。无使用者时启动可取消的延迟关闭任务；后台宽限期通过 A/B 测试调整，不机械删除所有保活。

验收：先启动 EasyTier，再播放完全缓存的远程曲目，确认无其他隧道任务时能够休眠；非绑定源直连不启动引擎；实际隧道长曲播放和下载不会被错误停止。记录子进程 CPU 时间与网络字节数后，再判断这项是否为设备上的主因。

## 5. 全局进度轮询缺少按需订阅和完整退出

[PlayerController.kt](../core/player/src/main/kotlin/com/mtechviral/musicfinderexample/core/player/PlayerController.kt) 151–203 行在 Application 初始化连接控制器后启动 ticker；1009–1033 行通过应用级主线程作用域持续循环。播放中 200 ms，暂停/空闲 2,000 ms，没有使用界面可见性或订阅者数量决定启停。

多数 Compose 页面已经使用 `collectAsStateWithLifecycle()`，这会控制界面消费状态，但不会停止独立启动的生产者 ticker。控制器断开（178–185 行）只清空引用，没有取消 ticker；循环会在 `controller == null` 时继续。如果断开时播放标记仍为真，还可能继续使用 200 ms 间隔。再次连接时 `startTicker()` 会取消旧 ticker，因此不能说 ticker 必然随重连无限累积。

此外，连接时创建的队列/模式订阅没有保存 Job，在断开时也没有取消；多次重连存在重复订阅风险，但不是已经证实的持续热循环。

建议仅在有可见进度/歌词消费者时启用精细轮询；暂停、结束、断开直接停止定时任务，状态变化依赖播放器回调。将控制器相关订阅纳入一个可取消作用域。验收时分别检查播放、暂停、熄屏、关闭悬浮歌词、断连重连的任务存活与回调数量。

## 6. 启动时补封面会造成隐蔽后台下载

[YuleMusicApplication.kt](../app/src/main/kotlin/com/mtechviral/musicfinderexample/YuleMusicApplication.kt) 55–94、101–107 行在应用初始化后台流程中查询所有待补封面的歌曲，调用 `cacheArtworkBatch()`，完成后重新加载曲库。[CacheService.kt](../core/cache/src/main/kotlin/com/mtechviral/musicfinderexample/core/cache/CacheService.kt) 430–438 行逐首处理，没有批量上限、充电/非计费网络约束，也没有退到后台后的暂停条件。

失败歌曲仍未缓存，下次进程启动会再次进入待处理集合；没有持久化失败退避。共享封面顺序处理时能命中已有文件，所以不能说“一张专辑封面必然下载多次”。不过封面缓存没有与音频缓存类似的在途去重，启动补缓存与播放页补封面并发时仍存在重复下载窗口。

建议先加载当前可见/正在播放条目的封面，将全库补全改成有预算的批任务；按数据源和封面 ID 去重，对失败记录退避。明确区分“进入后台”和“进程结束”：当前作用域不依赖 Activity，进入后台并不自动取消。

验收：大曲库首次打开后观察请求数、持续时间和传输量；服务器离线后不应在多次启动中重复执行无预算的全库重试。

## 7. 不应误判为根因的部分

| 项目 | 当前证据与判断 |
|---|---|
| `WAKE_LOCK` 权限及 `setWakeMode(C.WAKE_MODE_LOCAL)` | 播放器显式交给 Media3 管理，服务销毁时释放 player。权限存在不等于锁泄漏，应检查暂停后的实际持锁记录。官方说明 `setWakeMode()` 可自动管理锁的获取和释放。[Media3 故障排查](https://developer.android.com/media/media3/exoplayer/troubleshooting) |
| 播放页 16 ms 动画循环 | `NowPlayingUiState.kt` 76–96 行有 300 ms 时长和退出条件，是短时展开/收起动画，不能视为全天 60 fps 空转。 |
| 桌面小组件 | `music_widget_info.xml` 的 `updatePeriodMillis="0"`，状态更新由事件触发；未见固定周期刷新的证据。 |
| 扫描与文件读取中的 `while` | 多数有文件结束、游标、分页或挂起等待条件；仅检索到循环不足以认定忙等。 |
| 音频卸载 offload | 未见显式配置或运行状态观测，属于优化机会，不是已经证实的故障。官方指出熄屏长时间播放可能从 DSP 卸载受益，但依赖设备与格式支持。[Media3 电量消耗说明](https://developer.android.com/media/media3/exoplayer/battery-consumption) |

若“本地文件 + 悬浮歌词关闭 + EasyTier 从未启动 + 没有扫描/下载”仍明显耗电，应优先采集播放器解码、音频输出链路、实际 wake lock、CPU 调度和温度数据，不能继续把远程缓存当作该场景的解释。

## 8. 真机验证方案

### 8.1 固定条件

采用同一台真机、同一 release 构建、相同音源/音量/音频输出设备和网络信号。亮屏对照固定亮度；测试时不充电、不连接调试器，避免边充边测。短时系统跟踪可用于定位调用，正式耗电比较尽量减少日志与跟踪干扰。

每组建议 30–60 分钟，至少重复 3 次，交替测试顺序，记录温度和起止电量区间。百分比电量分辨率较粗，优先记录系统可用的电荷计数/功率数据、CPU 时间、网络字节数以及 wake lock 持续时间。系统电量页的“应用占比”与“整机每小时掉电百分比”需要分开记录。

### 8.2 对照矩阵

| 组 | 场景 | 目的 |
|---|---|---|
| A | 启动后不播放，退出界面，歌词关、组网未启动、无补缓存 | 测量空闲基线 |
| B | 本地文件熄屏播放，歌词关 | 音频播放基线 |
| C | 与 B 相同，悬浮歌词开；另做同条件亮屏对照 | 隔离歌词额外开销及熄屏工作 |
| D | 同一远程歌曲首次未缓存播放 vs 完全缓存播放；固定下一首缓存状态 | 核对播放流与整曲下载，避免预缓存混淆 |
| E | 先启动 EasyTier，再播放缓存曲；对照禁用引擎 | 验证错误保活及其成本 |
| F | 远程曲库大量封面缺失 vs 已补全；不播放 | 隔离启动补封面 |
| G | 连续点播不同未缓存歌曲后暂停 | 检查旧缓存任务数量、网络持续时间 |
| H | 本地播放暂停后退到后台，分别开/关悬浮歌词 | 确认暂停后的定时工作与真实持锁 |

D 组冷缓存与热缓存应使用事先准备的测试数据或可恢复数据副本，不直接清空用户的全部缓存。若测试关闭当前曲缓存或预取，需要单独测试构建；现有“缓存我喜欢”开关不控制这两条路径。

### 8.3 采集方法

具备 adb 环境后，可保存以下只读快照；当前报告没有执行这些命令：

```powershell
adb devices -l
adb shell dumpsys package com.mtechviral.musicfinderexample > package-info.txt
adb shell dumpsys battery > battery-before.txt
adb shell dumpsys batterystats com.mtechviral.musicfinderexample > batterystats-before.txt
adb shell dumpsys power > power-before.txt
adb shell dumpsys cpuinfo > cpu-before.txt
# 完成固定时长场景后，保存对应 after 文件，比较累计量差值。
adb shell dumpsys battery > battery-after.txt
adb shell dumpsys batterystats com.mtechviral.musicfinderexample > batterystats-after.txt
adb shell dumpsys power > power-after.txt
adb shell dumpsys cpuinfo > cpu-after.txt
adb bugreport power-analysis.zip
```

这些快照不替代完整时间序列：`cpuinfo` 是采样窗口，`power` 是时点状态，Batterystats 有累计统计边界。结合 Perfetto/Android Studio System Trace 查看 CPU 调度、频率、主线程与磁盘事件；能力支持时使用 Power Profiler。服务端日志按歌曲内容与时间段核对请求和字节数，区分 Range、重试与独立缓存请求。

重点观测 `PlayerController`、`FloatingLyrics`、`easytier-idle-watchdog` 及 `libeasytier.so` 子进程。可临时加入聚合计数：ticker 次数、歌词解析次数、偏好提交次数、活跃下载数、下载字节数、隧道租约数；避免为每个周期打印日志影响结论。

Android 官方目前提示 Battery Historian 已不再积极维护，建议优先使用系统跟踪、Macrobenchmark power metric 或 Power Profiler；Batterystats 仍可作为设备电量数据来源。[官方采集说明](https://developer.android.com/topic/performance/power/setup-battery-historian)

## 9. 修复顺序与交付边界

建议先改悬浮歌词的内存状态传递与重复解析，验证暂停/熄屏停止显示任务；随后合并播放和下载缓存链路并限制预取；再修正 EasyTier 按实际通道保活。每项独立做 A/B 验证，避免一次修改多项后无法确定收益来源。

之后处理播放器 ticker 生命周期和启动补封面预算。只有在上述额外工作受控、仍观察到较高的本地熄屏播放功耗时，再评估 offload 与设备音频链路。

本次交付为代码耗电风险分析和可执行的验证计划，仅新增本报告；未修改播放器行为，未运行构建或单元测试，也未完成真机功耗归因。
